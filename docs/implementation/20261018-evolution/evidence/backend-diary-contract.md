# R14 backend27 author contract

This work adds persisted personal diary state in the isolated diary worktree. It does not establish a shared clinical context or import browser history. The independently reviewed base26 publication ledger, generation routes and historical SQL/JSON contracts remain unchanged.

## Identity and provenance

The authenticated persisted active, non-deleted subject owns every day. Personal `tipo=usuario` with a valid non-OWNER role and a valid professional member can use the diary. A professional owner is excluded. Historical `tipo=usuario` with OWNER authority returns `409 diary_context_requires_review`; its type, plans, email or number of clients do not establish personal ownership. Existing generation authorities remain unchanged. The original independent export test that protects a portfolio whose owner changes persisted type is unmodified and passes under the definitive contract.

The first HTTP gate preserved `125 passed / 1 failed`: coordination's interim OWNER expansion contradicted that independent test. The expansion was withdrawn before integration; the new author test now verifies denial without adopting either own or mixed historical profiles. The initial four HTTP404 baseline failures and that first gate remain in their original evidence files.

Meal source lookup uses the base26 shared Plan JOIN Cliente reader: both owners must equal the authenticated subject and both rows must be live. An inactive historical client is allowed. Only server-resolved options, grams and nutrition become snapshots. A saved meal has its own source ID and UTC recording time; another menu or removal of the source Plan does not rewrite it. There is deliberately no Plan FK. No ID is inferred from time, similarity or a browser key.

## HTTP and transaction ownership

Full synthetic examples are in `backend-diary-http-contract.json`, generated by the current state and snapshot functions. Both web and API factories mount the same router.

* `GET /api/usuario/diario/{day}` returns persisted state or a virtual version0 day without DML or commit.
* `GET /api/usuario/diario` bootstraps today's calendar using the server's America/Mexico_City date. Both start/end omitted means today; one omitted means422. An explicit inclusive range has at most62 dates.
* `PATCH /api/usuario/diario/{day}` accepts only the existing discriminated water, meal or completion DTO. The body never chooses a subject or provides foods/macros. Future mutations are denied by the server-local date.
* An account UPDATE obtains the shared account write lock, then state is reloaded and its version compared. Expected0 creates only absent state. A successful operation returns the frozen snapshot of its own single commit, version expected+1. The local Session dependency does not autocommit at exit; GET never commits.
* A stale version gives409 and current_version. A failed or unacknowledged commit gives503, never a saved claim. The caller must reread before retrying. This is CAS, not an idempotency-key or automatic-merge protocol. Logs contain technical exception class only.

A new meal replaces only that meal and resets only its completion flag. Completion requires a saved snapshot and changes no foods or nutrition. Water changes no meals. `day.totals` sums all explicitly registered snapshots independently of completion; absent consumption has four zero totals. An explicit empty selection has an empty foods array and zero totals, not inferred consumption.

## Complete rejection and export

The adapter reads request chunks up to16KiB and rejects the first excess before JSON/DTO parsing or further stream reads. This is an application stream guard, not a global HTTP server or OS memory limit. Plan JSON is limited to256KiB before parsing, each selected group to256 options and each meal to32 foods. Stored meal JSON is validated in full before parsing/use:64KiB UTF-8, exact fields, finite nonnegative macros, verified totals, valid selections and UTC source stamp. Day/range responses are limited to1MiB. SQL CHECK bounds stored character length; the application separately enforces UTF-8 byte length. Corrupt or oversized content is rejected entirely, never truncated or replaced with zeros. Version arithmetic stops at2147483647.

Personal export adds a sixth `personal_diary` collection. Records include their UUID and unique local_date, full snapshots/totals, water/version/zone and UTC instants. `after_diary` is an exclusive ISO-date keyset cursor. `next_after` is the last emitted date only if more persisted days exist, otherwise null. Virtual days are not exported. Existing limit1..200 and128KiB per-collection budget apply; a page can contain fewer complete records. Professional portfolios and ambiguous OWNER contexts stay excluded. The export remains live keyset pages, not an immutable snapshot across requests.

## Schema and acceptance scope

Revision `20261019_personal_diary` follows `20261018_individual_publication` (wave26). It adds one table: **26 business tables,20 tenant families**, plus Alembic bookkeeping. Account FK uses RESTRICT, unique user/date prevents duplicate days, checks constrain zone/water/version/content. New UTCDateTime timestamps bind to existing UTC-naive SQL convention. The PostgreSQL policy is ENABLE+FORCE with matching USING/WITH CHECK by user_id. No grants, history import or legacy adoption occur.

The migration preflights the immutable exact26 structural and policy target before DDL. New27 SQLite/PostgreSQL fixtures and targets are separate files captured through real migrations; ORM DDL is only a test-fixture description. The historical publication migration test changes only implicit head/runtime expectations to explicit26, preserving all assertions and old fixtures. Failure after real diary DDL must roll back table, rows and revision. Downgrade requires reviewed rollback and verified restore rather than silently deleting diary data.

Author evidence is distinct from independent QA/security acceptance. PostgreSQL tests use only newly created UUID databases and the existing restricted app/migrator roles. Cluster port55482 was unavailable; QA authorized the same synthetic cluster on55483 without changing roles or the machine's other service. No production or provider operation was performed. Browser/UI, independent restore and security review remain separate acceptance work.

The initial oversized-source parametrization accidentally used a262KiB string as a pytest case ID; four setup errors were fixture path-length errors, not product failures. Short case IDs fixed the fixture without changing any assertion. Raw artifacts and the refused-port probe are preserved under Temp/metodobase-diary-fixture-errata-20261019 rather than committing multi-megabyte synthetic identifiers.
