# R07: metadata schema checkpoint

`20261018_stored_objects` follows `20261018_gym_generation_quota`: 25 business tables and 19 tenant families. Previous revision targets/fixtures remain immutable. New targets are captured from real SQLite/PostgreSQL migrations; SQL fixtures describe the model for tests and are never a production migration fallback.

`StoredObject` maps the existing `ObjectDescriptor` fields directly, with `gym_id` representing descriptor `owner_id`. Its UUID hex ID is 32 characters; `key` is unique and bounded to 512 characters. Checks constrain kind, backend, status, byte size (1 through 64 MiB), SHA256 length and content type length. The two timestamp fields use the previously accepted explicit `UTCDateTime` binder; physical columns remain without timezone.

`PlanGenerado.pdf_object_id` and `GymProfile.logo_object_id` are nullable. Their compound foreign keys `(gym_id, object_id)` reference `(gym_id, id)` on `stored_objects` with `ON DELETE RESTRICT`. The object's owner FK also uses RESTRICT. Existing `ruta_pdf` and `logo_url` values remain untouched, references remain NULL, and migration creates no object records or guessed associations. Database constraints enforce same-owner associations; application publication must additionally verify ready status, expected kind, backend and content integrity.

PostgreSQL enables and forces a transaction-local owner policy for the new table. Empty/missing tenant sees no records and cannot insert; foreign UPDATE/DELETE affect no rows, foreign inserts and moving own objects to another owner fail with SQLSTATE 42501. Same-owner metadata can be created, updated and deleted when unreferenced. Referenced metadata and owners with metadata cannot be deleted through existing cascade paths. No byte deletion, garbage collection or retention rule is introduced.

The migration preflights the exact accepted revision-24 structure and policies. SQLite table rebuilds run through blocking `db_bootstrap.py`, which temporarily suspends FK enforcement on its dedicated migration connection, uses an explicit transaction and requires an empty `foreign_key_check` before commit. The preservation fixture contains an existing plan, profile, client, completed quota record, durable result and legacy paths, then compares all old columns/rows after the upgrade and after a repeated run. Failure injection occurs after the first real plan table rebuild/ALTER, and verifies rollback of table creation, columns, revision and rows in both dialects.

Evidence: `backend-storage25-before.log`, `backend-storage25-final.log/xml`, `backend-storage25-schema-diff.json`, and `backend-storage25-source.json`. This checkpoint verifies local synthetic databases only. Object services, provider configuration, publication consumers and SDK behavior belong to the separate coordinator implementation.
