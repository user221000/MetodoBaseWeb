## R06: autor root, revisor seguridad

Se inspeccionaron `core/food_catalog.py`, `nutrition_validation.py`, `selector_alimentos.py`, los tres generadores, `estructura_comida.py`, `web/profile_schemas.py`, `web/routes/planes.py`, `api/schemas.py`, el cambio de `repository.registrar_plan` y la integración de perfil individual de backend. Se revisaron lectura de tenant, campos permitidos, finitud, catálogo por solicitud, fallbacks, validación final, orden respecto a PDF/persistencia y errores.

Observaciones comunicadas y resolución:

1. La excepción general de generación devolvía el texto de la excepción y podía filtrar parámetros/rutas. Root sustituyó respuesta por código `generation_failed`/mensaje estable y log de clase; ValueError usa `generation_unavailable` sin detalles internos.
2. Clientes todavía consultaba una feature comercial antes de guardar exclusiones. En el candidato integrado el catálogo ya habilitaba esa feature para todos, por lo que la nueva regresión Free/plan desconocido pasó incluso antes de retirar el check. La observación se corrigió en consecuencia: el check era inerte en ese estado, pero acoplaba seguridad a una futura decisión comercial. Seguridad retiró ambos checks con autorización de root, preservando validación, autorización y cuota. Ese cambio propio requiere revisión de backend; no se presenta aquí como aprobación independiente por seguridad.
3. `ConstructorMealStructure` todavía leía nutrientes/categorías globales. No reintroducía alimentos excluidos con los snapshots actuales, pero rompía el contrato de catálogo específico de solicitud. Root incorporó el mismo catálogo al helper y su validación.
4. `usuario_perfil.html` interpolaba exclusiones históricas en HTML. Root usa nodos/textContent/dataset al representar etiquetas, añade nombre al botón y retira promesas de interpretar diagnósticos/notas. La validación de backend limita IDs al catálogo. No se ejecutó un exploit XSS ni una evaluación completa de todos los sinks.

Resultado del alcance revisado: no se identifica una observación alta/crítica pendiente que permita restaurar alimentos excluidos en la ruta corregida. `FoodCatalog` congela estructuras anidadas, rechaza IDs desconocidos y falla si una categoría requerida queda vacía. Selectores y ajustes usan su tabla permitida; los fallbacks comprobados no pueden introducir alimentos fuera de ella. Ambos constructores verifican el resultado final antes de devolverlo al PDF web. Las notas se conservan para revisión humana; no se interpretan automáticamente.

Prueba repetida por seguridad tras las correcciones: `python -X utf8 tests/run_isolated.py tests/test_identity_security.py tests/test_nutrition_safety.py -q --tb=short`: **37 passed**, dos avisos de deprecación. Casos: rangos/NaN/infinito, contacto parcial, exclusión total, inmutabilidad profunda, rechazo final de alimento prohibido, selectores/ajustes simultáneos con restricciones distintas y generación completa de opciones. Límites: no prueba idoneidad clínica, contaminación cruzada ni grupos de alérgenos no modelados. R33 conserva revisión nutricional profesional, contrato completo y casos clínicos fuera del automatismo. Bandit B608 del downgrade: el nombre de tabla provenía sólo de una tupla literal interna de dos tablas, sin entrada externa. No se identificó SQLi explotable en ese flujo. Se pidió sustituir interpolación por SQLAlchemy expresivo para mantener el gate sin ampliar excepciones generales. Las pruebas de migración y rollback son una validación distinta.

## R08: autor root, revisor seguridad

Se inspeccionaron scripts de backup/restore, manejo de credenciales, temporales, manifiesto, GCM, rutas ZIP, comprobación de destino y errores. Se identificó y comunicó un fallo material: un manifiesto alterado podía seleccionar plaintext sin consentimiento del operador y sus hashes no autenticados permitían sustituir el dump. Root corrigió el formato con autenticación del manifiesto HMAC-SHA256 y clave derivada HKDF dedicada, antes de usar sus rutas/metadatos; selección cerrada de formatos; y modo plaintext explícito limitado a pruebas locales. Artefactos GCM se autentican antes de cualquier restauración.

La inspección confirma que credenciales PostgreSQL pasan por entorno al proceso, sin argv ni stderr en errores públicos; se comprueba nombre de base esperado y ausencia de tablas antes de restore transaccional. SQLite no sobrescribe destinos. ZIP se extrae en temporal, rechaza rutas absolutas, `..`, separadores Windows y `:`, comprueba lista/hash/tamaño y sólo luego promueve objetos. Fuente de objetos con symlinks o backup bajo su mismo árbol se rechaza. Una excepción no reporta backup completo; sin fuente tampoco hay éxito.

Seguridad repitió `python -X utf8 tests/run_isolated.py tests/test_backup_restore.py -q --tb=short`: **6 passed**, sin avisos. [security-backup-review.log](security-backup-review.log) y [security-backup-source.json](security-backup-source.json) conservan resultado/huellas. Los seis casos son SQLite/objetos sintéticos, cifrado/restauración, clave errónea/tamper, destino existente/incorrecto, exigencia de cifrado y manipulación de metadatos/downgrade. Los checks de traversal se inspeccionaron; no se afirma una prueba de penetración de ZIP. No se restauró PostgreSQL desde este agente: QA prepara ese ensayo aislado.

Referencias primarias consultadas: [Cryptography, API de cifrado simétrico y finalización GCM](https://cryptography.io/en/latest/hazmat/primitives/symmetric-encryption/) y [PostgreSQL 18, pg_restore](https://www.postgresql.org/docs/current/app-pgrestore.html). GCM sólo permite confiar en plaintext después de validar el tag. PostgreSQL advierte que restaurar un dump ejecuta las instrucciones definidas por su origen; por ello la autenticidad del backup y la confianza en su origen siguen siendo necesarias incluso con un destino vacío.

Resultado: sin observación alta/crítica pendiente en el mecanismo local corregido. Root también pasó sslrootcert al probe psycopg2 para conservar el mismo contrato TLS; se repitieron las seis pruebas después de ese cambio. Permanecen abiertos backup nativo Railway, política/gestión/rotación de claves, retención aprobada, consistencia entre PostgreSQL y objetos activos, restauración de la versión de producción y medición RPO/RTO. Los seis tests no acreditan por sí solos continuidad operativa ni cierran R08 completo.

## R05: autor QA, revisor seguridad

Se leyeron completos `conftest.py`, `tests/isolation.py` y `tests/run_isolated.py` congelados para A1. Sin observación alta/crítica pendiente en la preparación revisada: configuración se instala antes de importar la app; DATABASE_URL heredada se rechaza al invocar pytest directamente sin entorno preparado y el runner la sustituye; PostgreSQL sólo acepta host loopback, nombres de base/rol de test y ausencia de query/fragmento. Variables de proveedor/PG y dotenv quedan neutralizadas, datos y archivos temporales se separan por worker, errores de limpieza/fixtures fallan y cada caso elimina commits anteriores.

Los gates independientes de seguridad de 37 casos identidad/nutrición, 97 money y 6 backup utilizaron este runner. Son ejecuciones con solapamientos; no se suman como defectos ni casos únicos. El bloqueo de socket.connect/connect_ex limita TCP dentro del proceso Python: no es un sandbox de sistema operativo, no controla subprocesos arbitrarios ni garantiza aislamiento de un proveedor futuro. La lista de variables y adaptadores debe actualizarse antes de incorporar storage u otros servicios. PostgreSQL, paralelismo y Linux tienen evidencia separada de QA; esta revisión de código no suplanta esas pruebas ni la CI remota.
