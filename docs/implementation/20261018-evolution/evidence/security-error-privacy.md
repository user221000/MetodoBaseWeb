# Seguimiento R17/R31: excepciones globales y alertas automáticas

El hallazgo de compensación B2B reveló un segundo límite: ambos handlers globales registraban el texto completo de una excepción y podían adjuntar traceback. Un `StatementError` incluye SQL y parámetros; `ErrorAlerter.track_error` también copiaba `str(error)`, ruta con identificadores y todo `extra_context`, permitiendo además sobrescribir `error_type`.

[Ocho regresiones rojas](security-error-privacy-before.log) reprodujeron esas exposiciones con factories reales y alert history real, sin proveedores. [Test](../../../../tests/test_error_privacy_review.py). Los datos son marcadores sintéticos, no notas, identificadores o credenciales reales.

La corrección autorizada por root modifica únicamente estos límites de producto: `web/main_web.py`, `api/app.py` y `web/middleware/alerting.py`. Los handlers ahora registran exclusivamente la clase, sin `str`/`repr` de excepción ni `exc_info`, incluso en desarrollo. El handler API omite ruta y cliente al invocar el tracker. El tracker conserva clase y contador; de `extra_context` sólo acepta `method` si coincide con una lista cerrada de verbos HTTP. El argumento histórico `request_path` sigue aceptándose para compatibilidad, pero no se retiene. Metadata libre, IP, URL, token, notas y override de clase quedan fuera del historial/alerta automática.

Root corrigió por separado la compensación B2B en ambos adapters y un helper compartido: rollback y liberación quedan dentro del límite protegido; si fallan, HTTP 503 `generation_reconciliation_required` dirige al historial y conserva la reserva, sin afirmar devolución. El identificador de reserva se captura antes del trabajo. La revisión de esa corrección incluye el nuevo caso de rollback fallido: no intenta liberar después de perder certeza de la transacción ni registra parámetros del error.

El gate final combina nueve controles de handler/alertas/rollback con las cuatro regresiones B2B independientes; [resultado](security-error-privacy-after.log), [JUnit](security-error-privacy-after.xml), [fuentes](security-error-privacy-source.json). Los factories y el principal/tenant de B2B son reales. Sólo CPU y compensación indisponible se doblan explícitamente para el error B2B; el caso de rollback usa un Session double para forzar ese fallo preciso. Las alertas conservan su lógica de spike, severity y cooldown; las pruebas desactivan los notificadores y verifican el payload retenido, no una entrega externa.

Este seguimiento no declara saneados todos los logs de la aplicación, el ingreso HTTP del hosting, los eventos automáticos de Sentry, los mensajes enviados mediante `send_alert` directo ni las excepciones propias de transportes de notificación. Esos límites requieren su revisión específica. Tampoco borra logs históricos ni modifica retención o permisos externos. La contención reduce los datos nuevos que estos handlers/tracker incorporan; R17/R31 mantienen el resto de criterios abiertos.
