# R04: contrato de activación y separación de roles

La revisión 20261018_tenant_isolation conserva las 23 tablas de la preparación. Su vocabulario de 17 familias está congelado dentro de la migración. Reemplaza sólo las políticas conocidas; una política adicional o desconocida aborta antes de modificar la protección. Todas las familias usan ENABLE y FORCE y el mismo predicado para USING y WITH CHECK. NULL y cadena vacía no conceden filas. El helper histórico se reconcilia a SECURITY INVOKER y configuración local a la transacción; no lee datos.

El manifiesto por revisión añade tenant_security: banderas de las 23 tablas, definiciones/roles/comandos de las 17 políticas y definición/configuración/seguridad de set_tenant. El arranque compara este contrato además de la estructura. Desactivar FORCE, desactivar RLS, añadir una política permisiva o convertir el helper a SECURITY DEFINER impide arrancar. Los manifiestos de R03 y preparación permanecen intactos y pueden ensayarse con --revision explícita.

Las fábricas web y API verifican el esquema antes de inicializar auth y rechazan superuser, BYPASSRLS y pertenencia directa o indirecta a cualquier propietario de tablas de la aplicación. FORCE por sí solo no impide que un propietario altere la tabla. El control usa pg_has_role(..., 'MEMBER'), cuya semántica está documentada por [PostgreSQL 17](https://www.postgresql.org/docs/17/functions-info.html#FUNCTIONS-INFO-ACCESS-TABLE): la pertenencia directa o indirecta se detecta aunque no otorgue privilegios inmediatos. El ensayo modifica únicamente el propietario de clientes dentro de la base UUID propia; no cambia pertenencias del rol compartido.

En producción db_bootstrap exige MIGRATOR_DATABASE_URL explícita además de DATABASE_URL de la aplicación. Verifica PostgreSQL, mismo host/puerto efectivo/base y roles distintos antes de conectarse. Usa un engine efímero propio, lo libera al salir y nunca toma SessionLocal ni sustituye DATABASE_URL. Local/testing conserva DATABASE_URL explícita para ensayos históricos. El entrypoint debe retirar MIGRATOR_DATABASE_URL del entorno antes de ejecutar el servidor. No se imprimen URLs ni credenciales.

Evidencia del autor: primera tanda 89 aprobadas y un error de fixture de token corregido por QA; segunda tanda de canales 6 aprobadas (token canónico, perfil personal y dos flujos HTTP PostgreSQL de invitación/revocación para miembro usuario y gym histórico). Las regresiones de propietario de tablas dieron dos fallos antes del control y después pasaron ambas fábricas. Contrato final de URLs: 22 pruebas aprobadas, incluidas las cuatro negativas independientes de QA para overrides del driver. La allowlist admite sólo opciones TLS; host/base explícitos y roles distintos se comprueban antes de crear el engine.

Aceptación independiente local comunicada por QA: 64 casos de matriz y DML, restore de 23 tablas con FORCE, y 37 casos de seguimiento PostgreSQL (17 sin tenant, 10 de activación/propietario/arranque, dos de onboarding, dos de invitación y seis de callbacks activados). CLI más guarda del harness: 23 aprobadas. El coordinador ejecutó además 38 pruebas de activación/CLI/entrypoint/perfil personal. No cambió producto durante los gates finales. La operación real y cuota B2B permanecen sujetas a sus gates separados; la separación de seis tablas de control sigue explícita en la matriz.
