# Adenda31: vigencia original del segundo factor

El contrato inicial se conserva sin sobrescribir. Los cuatro archivos `pre-recent-witness-*` son las preimágenes RAW exactas del modelo, migración y dos primeros targets31 WIP. Los targets22–30 no cambian. Esta adenda todavía no declara aceptación independiente ni despliegue.

`mfa_authorizations.factor_verified_at` es un instante UTC tipado. Una verificación de login confirma su valor junto con `consumed_at` y el refresh. Un permiso de acción registra el instante de la verificación que lo autoriza. Reutilizar una verificación reciente para emitir otro permiso conserva ESE instante; nunca escribe la hora de la nueva consulta como si fuera una autenticación. La consulta sólo considera mismo actor, SV, generación y hash exacto del acceso firmado. No puede copiarse a otro acceso aunque ambos pertenezcan a la misma cuenta. Refresh conserva la hora MFA original de login y no copia un testigo posterior ligado a otro acceso.

La ventana técnica es de cinco minutos con intervalo cerrado al inicio y abierto al final: `0 <= now - factor_verified_at < 300s`. Un instante futuro no acredita autenticación. El vencimiento de cada permiso es `min(factor_verified_at + 300s, access.exp)`. Emisión, lectura, consumo y refresh no amplían ese límite. Cambiar factor, revocar sesiones, cambiar pertenencia o desactivar la cuenta corta la autoridad mediante generación/SV/identidad persistida. Reutilizar un código OTP sigue prohibido; una nueva verificación real necesita otro contador válido o un código recovery todavía sin usar.

Se verifica MAC, propósito access, issuer, audience, expiración y contexto contra la identidad ya bloqueada. No se abre otra Session para verificar el mismo token: un pool de una conexión también debe operar. Actor nulo, SV distinto, generación distinta, timestamp de tipo inválido o acceso diferente no heredan testigos. El servicio rechaza una transacción anidada en estas operaciones para evitar restauraciones de capacidad LOCAL ambiguas tras savepoints.

La reautenticación primaria de Google exige `auth_time` verificado y reciente. `iat` no sustituye ese dato. La UI debe solicitar la metadata esencial y provocar una autenticación primaria real; ausencia o antigüedad produce rechazo, no una caída a un access/refresh recién emitido. El transporte de pruebas es sintético y no acredita disponibilidad ni configuración de Google reales.

La transacción de negocio consume el permiso junto con la mutación o la intención durable antes de salir a un proveedor. Un commit fallido o con ACK perdido produce503 opaco; no se devuelve éxito, seed, código recovery ni token por una confirmación incierta. El consumo durable tras perder el ACK puede exigir un permiso nuevo al reintentar, manteniendo la idempotencia financiera existente. No hay compensación que resucite un permiso ya confirmado.
