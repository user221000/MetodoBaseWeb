This is an isolated local implementation in `F:/MetodoBaseWeb-recovery-20261019`, based on accepted diary27. ## Public contract

- `GET /auth/reset-password`: public first-party form; no-store, no-referrer, nosniff. A fixed CSP in SecurityHeadersMiddleware applies only to this exact path. It uses the existing request nonce and permits same-origin script/style/connect/form only; other paths retain their prior policy. Downstream arbitrary CSP is never trusted. Both login templates gain a plain recovery link; their script blocks are unchanged.
- `POST /api/auth/password-reset/request`, JSON `{email}`: 202 with `code=password_reset_request_received` and the same generic message for eligible, absent or ineligible accounts and all later mail outcomes. Syntax/type errors are 422, body overflow413, content type415. Missing global mail/origin/production Redis configuration or a full dispatcher is uniformly503 before lookup/admission. Rate limit429 retains Retry-After. All recovery API responses, including parser/service errors, have no-store/no-referrer.
- `POST /api/auth/password-reset/confirm`, JSON `{token,new_password,confirm_password}`: 200 `password_reset_complete`, without access/refresh tokens or automatic login. Invalid/expired/used/ineligible/version-changed bearer returns400 `password_reset_unavailable`. A possible commit failure returns503 `password_reset_unconfirmed`; it does not claim that the password stayed unchanged. The UI clears secrets and explains normal login with the new credential or requesting another link.

Both bodies are read from the ASGI stream into at most4096 bytes before parsing. A chunk crossing the limit is rejected before JSON/TypeAdapter and before requesting further chunks. This is a route-level read/parse budget, not a global server/middleware limit. Additional fields are rejected and public errors never echo input.

Passwords use the shared existing minimum12 characters plus an explicit maximum72 UTF-8 bytes required by the pinned bcrypt implementation. Current stored password verification is unchanged. Email normalization remains strip+lower; no aliases, casefold merging, account association, roles or ownership are introduced. Registration, password login, Google account lookup, invitation DTO/service and account limiter use the shared narrow helpers.

## Existing authority and transaction

Only Usuario gains three nullable fields: `password_reset_hash`, `password_reset_expires_at` (UTCDateTime), `password_reset_session_version`. UNIQUE digest and all-or-none CHECK are enforced. Existing rows receive NULLs. No new authority table or RLS exception is created: there remain26 business tables and20 tenant families. Auth control-plane access is the existing account lookup, not a caller-selected gym.

The opaque bearer contains256 random bits, encoded as43 URL-safe characters; only SHA256 of a purpose-prefixed bearer is stored. Its30 minute TTL is an explicit technical policy. Active/live accounts with valid persisted role/type and valid professional membership can recover credentials; pending invitations and inactive/deleted/invalid accounts are excluded. An owner may recover their own credential; recovery grants no personal-space or portfolio authority.

Issuance acquires the account lock, reloads eligibility/email/version, stores digest/expiry/version and a minimal audit event, then commits. Session/connection/lock are released before the mail port. Each new issuance replaces the previous bearer. Requesting recovery does not change password, active flag, session_version, role, membership, portfolio, quota or existing refresh tokens. Commit uncertainty sends nothing and performs no compensation.

Consumption resolves the subject from the bearer, rejects an ambient different subject, hashes the new password outside the long lock, acquires Usuario first and reloads/revalidates expiry/eligibility/version/digest. One conditional update changes the password, increments session_version and clears all three reset fields. Refresh revocation and the minimal completion audit event join the same transaction and single commit. Failure before commit rolls back; an ACK lost after the real commit retains all committed effects. No second finalizer commit, helper-owned transaction, password rollback or adoption by input ID exists.

Logout and the refresh-reuse second transaction now acquire Usuario before RefreshToken. Their prior revocation semantics and root's success acknowledgement remain. A refresh pair emitted late from a pre-reset identity carries its old SV and is rejected by normal persisted identity verification.

## Mail and bounded admission

The dispatcher admits at most32 running+queued jobs per process with2 workers, using fresh Context for each job. HTTP does not look up an account or wait for mail/SDK. A blocked synthetic SDK test confirms the complete ASGI response and health response return while the worker remains blocked. Shutdown cancels work that has not started; SDK transport timeout controls running work. The installed SDK source has a30 second requests/httpx timeout; this is not a promise of durable queueing or wall-clock delivery.

The queue contains normalized email in process memory. Bearers remain in worker/template transport memory and the browser closure; there is no plaintext token outbox, browser storage, URL query, logger field or metric label. Configured BASE_URL is validated as a pure trusted origin; production uses HTTPS, development HTTP only loopback. Request Host/forwarded Host never supplies the link origin. The bearer is in the fragment, removed immediately by history.replaceState before form interaction. A GET/email scanner cannot consume it.

The added email templates use the unchanged root SDK serialization and valid ACK-id requirement. True means provider acceptance, not delivery. False, invalid ACK, exception or timeout remain unconfirmed and never alter public202 or roll back an issued digest. A process crash may lose an admitted request or leave an unsent issued digest; a new request replaces it. Password-change notice is postcommit best effort and cannot undo the change. No retention/GC or encrypted durable outbox policy is invented here.

Recovery limits are separate HMAC namespaces: request5/900s IP and3/900s email; confirm10/900s IP and10/900s token. Production requires configured Redis and uses its sensitive fail-closed path. Explicit development/testing can use the existing bounded local limiter. Recovery does not bypass its own limiter through the general disable flag. Existing login remains available if recovery configuration is disabled; an already-issued valid link can be confirmed without the mail key, subject to production limiter availability.
