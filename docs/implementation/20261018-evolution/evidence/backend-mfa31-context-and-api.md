## Contexto de secretos

`app.mfa_actor` es una capacidad LOCAL exclusiva de `mfa_credentials` y `mfa_recovery_codes`. Sus políticas sólo comparan `user_id` con ese valor; el tenant profesional no da acceso a factores. El BEGIN de cada conexión lo pone en vacío, incluso si alguien dejó un valor session-level. El servicio lo instala con parámetro SQL sólo después de verificar Usuario persistido y, al mutar, adquirir sus locks; los queries añaden el user_id del actor. No procede de un body, JWT sin validar, email o gym_id UI. Un SET fallido aborta antes de consultar secretos. Commit/rollback/pool no transportan esa capacidad a la siguiente transacción. No cambia ninguna política22–30.

## MFA reciente

Un login MFA confirmado incluye `amr`, `mfa_generation` y `mfa_at` firmados por el servidor en el token de DOS partes. Refresh conserva ese instante original; no lo sustituye por iat/exp ni convierte una sesión primaria en MFA. Durante5min desde la verificación puede solicitarse un grant sin introducir otro OTP; cada grant sigue siendo distinto, de un uso y ligado al access EXACTO/actor/SV/generación/acción/recurso/body/key. Después de5min hace falta una prueba OTP/recovery nueva. Se comprueban los claims del access verificado y la generación/SV persistidas; nunca se aceptan esos claims en DTO. Este período técnico limita la repetición de prompts, no añade un dispositivo confiable ni cambia permisos.

Enrolar/reemplazar, regenerar códigos y revocar necesitan SIEMPRE una reautenticación primaria nueva, de un uso y ligada al access. Reemplazar/regenerar/revocar también necesitan el factor vigente. MFA reciente por sí sola no permite estos cambios. El enrolamiento y una autenticación OTP consumen su contador; no se reacepta ese OTP para otra autenticación. Si hace falta otra prueba en el mismo intervalo, se espera el siguiente código o se utiliza un código recovery aún no usado.

## Formas de respuesta

Login primario sin factor conserva200 y campos `token, refresh_token, tipo, role, team_gym_id, nombre, email`; añade `mfa_required:false`. Con factor devuelve202: `{mfa_required:true, challenge:<bearer43>, expires_at:<UTC>, methods:["totp","recovery_code"]}` sin tokens. El challenge es memoria efímera del formulario, nunca URL/Storage ni una sesión profesional. `POST /api/auth/mfa/login/verify` recibe challenge y exactamente code o recovery_code;200 devuelve tokens sólo después de COMMIT confirmado.

`GET /api/auth/mfa/status` devuelve `enabled,pending,recovery_codes_remaining,methods,required_for_privileged_actions,totp_period_seconds:30,challenge_lifetime_seconds:300`; no recupera un seed pendiente. `POST /reauth` admite exactamente password o google_credential y devuelve `reauthentication_token,expires_at`. `POST /enroll` recibe ese token y, si reemplaza, code/recovery_code vigente. Devuelve una vez `enrollment_id,secret,otpauth_uri,expires_at,shown_once:true`. `POST /enroll/confirm` recibe enrollment_id+code y devuelve `success,enabled:true,recovery_codes:[8],shown_once:true,reauthenticate:true`; sesiones anteriores quedan invalidadas. `/recovery-codes/regenerate` devuelve kit nuevo una vez y reauthenticate; `/revoke` devuelve enabled:false y reauthenticate. Las dos requieren reauthentication_token y factor.

`POST /step-up` recibe `{method,path,body,idempotency_key?,code?,recovery_code?}`. Ausencia de ambos factores significa usar evidencia MFA reciente válida; ambos presentes es422. Método/ruta/body se validan con el registro cerrado de acciones y DTO real de destino. Respuesta200 `{grant,expires_at,action,method,path,single_use:true}`. Consumidor añade `X-MFA-Grant` a ESA petición exacta. Normalización de DTO incluye sus defaults; una clave Idempotency-Key usada en la acción financiera se fija también al emitir el grant. No resolver recursos latest ni cambiar un body observado silenciosamente.

Errores con `detail:{code,message}`:401 `mfa_identity_unavailable`;403 `mfa_enrollment_required`, `mfa_step_up_required`, `mfa_fresh_verification_required`, `mfa_action_forbidden` o `mfa_action_mismatch`;400 `mfa_proof_unavailable`, `mfa_verification_failed`, `mfa_enrollment_unavailable`;409 `mfa_busy`/`mfa_grant_consumed`;413 `mfa_input_too_large`;422 `mfa_invalid_input`/`mfa_action_invalid`;429 `mfa_throttled`;503 `mfa_service_unavailable`/`mfa_unconfirmed`. Un503 no autoriza inferir rollback, repetir un grant consumido ni mostrar éxito. Reconsultar estado o realizar login/challenge nuevo. Formulario nunca imprime el body técnico de un error no esperado.

Body MFA máximo32768bytes acumulados durante lectura de stream, antes de parsear; se rechazan duplicados, no finitos, campos extra y tipos coercitivos. No es una promesa del máximo de buffers del servidor/middleware. Todas las respuestas MFA, también405/429/503/500, tienen no-store/no-referrer y CSP first-party fija. Login con challenge también no-store/no-referrer. TLS, protección del terminal, despliegue de clave independiente y UI/revisiones siguen siendo gates operativos. No hay evidencia de resistencia al phishing con TOTP.
