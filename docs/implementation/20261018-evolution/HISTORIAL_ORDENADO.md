# Historial ordenado, revisión30

Candidato aislado para R34. Se apoya en el núcleo29 corregido y sus cuatro casts PostgreSQL estables al restaurar. La aceptación de API/UI29 y la integración de esta revisión se registran por separado.

El ensayo HTTP de200 solicitudes detectó una consulta de50 resúmenes que examinaba1000 planes. El primer prototipo de índice mejoró la primera página, pero el cursor avanzado seguía recorriendo1000 filas. Por eso se conservan tanto las evidencias anteriores como las consultas y planes nuevos; no se atribuye una mejora de p95 causal a estas observaciones.

La consulta compartida conserva los predicados explícitos de propietario del plan y del cliente, perfil y borrado lógico. Selecciona nueve campos de resumen, sin cargar `plan_json` ni contar el historial. La página inicial y un cursor sin fecha usan una consulta limitada; un cursor fechado usa dos ramas limitadas a `limit+1` (fechados anteriores y filas sin fecha), unidas en una sola sentencia y snapshot. El resultado externo conserva el orden fecha descendente, NULL al final, e identificador descendente. El máximo de candidatos entregados por ambas ramas es `2*(limit+1)`; esto no es una garantía universal de filas físicas examinadas por todo planificador o distribución.

El índice parcial `ix_planes_gym_cliente_history` contiene `(gym_id,id_cliente,fecha_generacion DESC NULLS LAST,id DESC NULLS LAST)` en PostgreSQL, sólo para planes vivos. SQLite usa DESC para ambas columnas y su orden nativo de NULL. Se conserva el índice anterior por gimnasio/fecha. No se modifica una fila, cuota, permiso, cursor firmado o contrato HTTP.

La primera prueba mixta tuvo un fallo real:107 filas examinadas con presupuesto102. El plan de la rama sin fecha escogía la clave primaria hacia atrás y filtraba otras historias. Declarar NULLS LAST también en el identificador y en la consulta hace coincidir los pathkeys del índice nuevo. El identificador es NOT NULL, por lo que el resultado sigue siendo idéntico. El replay dirigido midió51/52/51/51/51 filas en primera página, empate, cursor avanzado, transición a NULL y cursor NULL, con los mismos1000 resultados completos, sin duplicados ni asociaciones cruzadas. No se cambiaron parámetros del planificador ni estadísticas de coste para obtenerlo.

El formato estructural histórico v1 no representa dirección, orden de NULL o colación de un índice. Se conserva inmutable y se añade un contrato físico adoptado sólo desde30: columnas, dirección/NULL PostgreSQL, método, estado válido/listo, unicidad, predicado, colaciones y clases de operador; SQLite comprueba sus campos equivalentes. Startup y downgrade rechazan un índice ausente o alterado aunque el formato v1 coincida.

La migración exige el esquema29 exacto y sus contratos de seguridad antes de crear el índice; comprueba el30 completo antes de confirmar. El downgrade verifica30, elimina únicamente este índice y comprueba29. La prueba de fallo inyectado después del DDL debe conservar filas, permisos y marcador29 por rollback real. Los datos sintéticos incluyen los de recuperación, diario y publicación individual de versiones anteriores. No se amplían normalizadores, targets22–29 ni políticas RLS históricas.

Para una futura ejecución operativa, este CREATE INDEX transaccional toma un bloqueo que puede frenar escrituras. Hace falta una ventana revisada, respaldo/restore, comprobar tamaño/recursos y fijar límites de espera/ejecución adecuados al entorno antes de autorizarlo. Esta ejecución local no mide capacidad productiva ni promete un despliegue sin bloqueo. Los demás flujos, colas, objetivos de p95 y datos representativos de R34 siguen abiertos.

Fuentes primarias: [orden e índices PostgreSQL17](https://www.postgresql.org/docs/17/indexes-ordering.html), [CREATE INDEX de SQLite](https://www.sqlite.org/lang_createindex.html) y [DDL condicional de SQLAlchemy2](https://docs.sqlalchemy.org/en/20/core/constraints.html#sqlalchemy.schema.HasConditionalDDL.ddl_if). Se aplican a las versiones locales registradas; no se actualizaron dependencias para esta implementación.
