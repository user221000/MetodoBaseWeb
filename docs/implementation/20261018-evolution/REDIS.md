# Rate limiting y degradación del candidato

R17 parcial. Implementado en `web/rate_limiter_redis.py`, `web/rate_limiter.py` y `web/middleware/rate_limiter.py`. Redis configurado comparte contadores entre procesos mediante un script Lua atómico. INCR y creación/reparación de TTL ocurren juntos; las solicitudes siguientes, incluidas las rechazadas, no extienden el TTL. Base técnica: [ejecución Lua atómica](https://redis.io/docs/latest/develop/programmability/eval-intro/) y [patrón INCR/EXPIRE](https://redis.io/docs/latest/commands/incr/), consultadas el 18 de octubre de 2026.

Si falla Redis, autenticación, invitaciones, generación y compras sensibles devuelven 503 con código público `rate_limit_backend_unavailable` y Retry-After de 5 segundos. No se llama al handler. Las lecturas y logout conservan un fallback local limitado, señalado con `X-RateLimit-Backend: local-degraded`; al excederlo devuelven 429. Salud no consume Redis. Un timeout incierto puede haber consumido un intento; no se concede permiso suponiendo que no ocurrió.

La dependencia de login usa ahora 5 intentos por 900 segundos, corrigiendo la implementación anterior que ignoraba la ventana y usaba un burst de 1. Añade contador por correo normalizado cuando el JSON lo contiene; la clave es HMAC con separación de propósito y secreto del servidor, sin almacenar el correo en Redis. Google conserva el límite por IP porque su entrada no contiene correo sin verificar. Las claves de ruta usan el template resuelto para no multiplicarse por identificadores dinámicos.

Sin Redis configurado, los almacenes locales continúan disponibles pero sólo limitan cada proceso. Ambos tienen máximo de 10 000 buckets y rechazan identidades nuevas al llenarse, después de recuperar entradas inactivas. La limpieza respeta la ventana de cada bucket. No se presenta este modo como protección distribuida.

`TRUSTED_PROXY_COUNT=0` ignora X-Forwarded-For/X-Real-IP. Con N proxies verificados se selecciona XFF[len(XFF)-N], contando el socket peer como último proxy. Un despliegue que confíe en proxies debe impedir acceso directo y sanear las cabeceras en el ingreso. Se validan IPs y longitud de la cabecera; entradas inválidas vuelven al peer del socket. No registrar las claves, correos, URLs Redis ni excepciones completas. La [documentación de Railway](https://docs.railway.com/networking/public-networking/specs-and-limits) publica X-Real-IP como dirección remota; el contrato XFF concreto del despliegue debe verificarse antes de aceptar ingress. No se afirma validado por estas pruebas locales.

Métricas de proceso incluidas en el resumen existente: estado observado, fallos, recuperaciones, rechazos sensibles y solicitudes fallback. La transición a degradado genera un warning saneado; la recuperación genera un evento informativo. Las métricas no son agregados del cluster ni prueban que una alarma externa esté configurada. R17 sigue abierto para alertas de webhooks/cola/backup/correo y validación operativa.

Ante un incidente: consultar estado/latencia del servicio y conectividad/TLS/ACL mediante herramientas autorizadas; revisar el evento saneado de degradación; recuperar Redis y verificar una transición de recuperación más una solicitud dentro/fuera de límite. No vaciar contadores globales, imprimir secretos o desactivar límites como respuesta al incidente. La disponibilidad de lecturas y logout no autoriza una compra o generación sin verificación.
