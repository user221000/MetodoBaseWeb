# UI34: tareas de seguimiento

La página `/seguimiento` y la ficha `/clientes/{id}/seguimiento` permiten consultar tareas autorizadas, preparar una creación por causa vigente, editar paso y responsable, registrar una revisión completada o cancelar con motivo cerrado. Cada escritura exige confirmación; cargar, filtrar, abrir una ficha o consultar cifras sólo hace lecturas. El dashboard conserva sus hechos y muestra tareas abiertas por causa con próximo paso y responsable.

El servidor fija el alcance. OWNER/ADMIN gestiona su gimnasio; Nutri recibe sólo sus asignaciones y puede completar las tareas permitidas. La página tiene shell propio y no carga estadísticas globales ni el sidebar heredado. Los nombres de responsables no elegibles permanecen nulos; no se buscan contactos. Las fechas de membresía no prueban deuda y una revisión completada es una declaración del actor, sin contacto, entrega, cobro, renovación ni efecto clínico inferido.

`Api.followup` fija rutas, cuerpos, versiones y cursores. Las operaciones tienen UUID idempotente y cuerpo capturado en un handle opaco en RAM, vinculado al acceso exacto. El transporte no rota credenciales, reintenta ni consulta el resultado después de escribir. El ACK debe corresponder a la clave de operación, recurso, cliente, causa, versión, paso, responsable y tiempo esperados. Un replay confirma una operación histórica y obliga a consultar expresamente el estado actual. Una respuesta incierta bloquea otra preparación hasta una lectura primaria explícita; consultar métricas o responsables no desbloquea un DTO viejo.

La historia pagina por versión ascendente. Las cifras separan estado actual de eventos del periodo y muestran fuente, cobertura de clientes activos y zona America/Mexico_City. No se convierten errores en ceros. Los formularios usan diálogo nativo, labels, regiones status/alert, confirmación, Escape y retorno lógico de foco; el adaptador sólo utiliza textContent para datos. Se limpian datos visibles y ocultos por cambio de sesión, Storage, pagehide y retorno de bfcache.

Validación de autor: 72 casos VM/DOM propios y 15 casos SSR/privacidad/compatibilidad entre DTO HTTP SQLite reales y parsers JavaScript. Ambas factories pasan, incluidos alias //307 con Location exacta y headers privados. La fase final mantuvo 1076 fuentes, 92 paquetes y Python/Node quietos, con pip check con salida 0 antes y después. Las 17 suites previas de regresión auth/MFA/Google/dashboard (245 casos) están conservadas con su fuente y ejecución propias. Otro comando sólo cargó un helper y no ejecutó casos de login; no se suman ejecuciones superpuestas.

La evidencia conserva el namespace ausente inicial, los dos canarios de bloqueo que fallaron durante WIP y la transición de framing del alias SSR. No afirma revisión independiente ni aceptación Chrome, layout en 320/390/768/1440, axe, PostgreSQL, instalación desktop, proveedor real, rendimiento o despliegue. El almacenamiento global heredado de tokens sigue abierto para R31: el bloque nuevo no lo altera, como acredita la inversa exacta de api.js.
